# 主 Agent 托管与编排模型

> 省心模式：用户只与最可靠的主 Agent 对话，后台专业能力由主 Agent 调用、审查和验收。

## 1. 采用什么模式

默认模式是 **Manager Pattern / Orchestrator–Worker**：

- Manager 是面向用户的主 Agent，保留对话控制权和最终责任。
- Worker 是被调用的专业能力，只处理边界清楚的子任务。
- 多个独立 Worker 并行时采用 fan-out / fan-in：主 Agent 分发，等待结果，再统一整合。

这不是 Handoff。子 Agent 不接管用户对话，用户也不需要学习如何指挥多个 Agent。

## 2. 单一责任入口

| 参与者 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 用户 | 表达目标、感受、限制，确认重要方向和外部副作用 | 给技术问题分类、拆子任务、管理多个 Agent |
| 主 Agent | 语义理解、阶段判断、架构、路由、冲突裁决、验证和交付 | 把未经检查的子 Agent 输出直接交给用户 |
| 子 Agent | 完成被委派的具体任务，返回产物、证据和风险 | 扩大范围、改变产品方向、独立宣布完成 |

无论调用多少子 Agent，用户最终只收到一个由主 Agent 负责的结果。

## 3. 从问题到执行的路由

```text
理解用户表达
→ 判断协作模式和项目阶段
→ 选择本轮交付物
→ 形成问题单和最小垂直切片
→ 委派价值闸：NO_DELEGATION 或 DELEGATE
→ 选择执行配置：角色、模型、推理、权限、验收
→ 主 Agent 直接执行或 Worker 执行
→ 主 Agent 审查、验证、统一交付
```

角色描述“做什么”，模型层级描述“由多强的模型做”，推理预算描述“本轮投入多少思考”，
权限描述“允许影响什么”。四者相互独立，不得用模型能力推导权限。

### 记忆输入与结果反馈

编排开始前，主 Agent 只读取与当前范围和任务相关的已验证记忆或必要历史线索；
待复核内容必须用当前代码、测试、配置或真实输出重新验证。编排完成后，问题单、尝试、
测试结果、修复证据、决定和新风险进入项目候选，而不是自动写入全局。

因此编排不是记忆的下游终点：记忆帮助主 Agent 更准确地理解意图和选择路线，执行证据
又反过来提高记忆质量。完整闭环见[双引擎成长蓝图](EVOLUTION_BLUEPRINT.zh-CN.md)。

## 4. 执行配置与当前默认映射

主 Agent 不只选择模型，而是选择一份可追踪的执行配置：

```text
执行配置
= 任务角色
+ 模型层级
+ 推理预算
+ 权限范围
+ 输出与验收
+ 时间预算
+ 升级条件
```

| 能力层级 | 默认用途 | 当前 Codex 映射 |
| --- | --- | --- |
| Frontier | 主编排、架构判断、冲突裁决、高风险复核、失败重规划 | Sol / `gpt-5.6-sol` |
| Balanced | 常规开发、测试分析、代码调查、文档研究 | Terra / `gpt-5.6-terra` |
| Fast | 搜索、分类、抽取、格式转换、大批量只读扫描 | Luna / `gpt-5.6-luna` |

模型层级与推理预算分开选择。同一 Fast 或 Balanced 模型可以按任务难度使用不同推理预算；
推理更深不会自动扩大文件、数据、凭据或外部写入权限。

| 权限级别 | 允许范围 |
| --- | --- |
| P0 只读 | 搜索、查看、分类、分析和抽取 |
| P1 隔离写入 | 在已授权任务 worktree 中修改代码、测试和文档 |
| P2 非生产操作 | 运行测试、构建或经过隔离的 staging 操作 |
| P3 真实副作用 | 生产部署、数据迁移、外部写入和权限修改；必须由主 Agent 复核并取得用户明确授权 |

一期保持少量稳定配置，不为每个任务名称创建一个 Agent：

| 执行配置 | 默认能力 | 适用范围 |
| --- | --- | --- |
| `DIRECT_MAIN` | Frontier，推理按需 | 小型直接任务、意图与架构判断、高风险决策、最终整合 |
| `FAST_SCAN` | Fast Low / Medium | 边界明确、结果可抽查的 P0 批量只读工作 |
| `BALANCED_WORK` | Balanced Medium / High | 边界清楚、可测试验收的 P0 / P1 调查、开发、测试和文档 |
| `INDEPENDENT_CHECK` | Balanced High | 独立复核、测试分析和证据核查，默认 P0 |
| `ESCALATE_TO_MAIN` | 返回 Frontier 主 Agent | 范围、风险、权限或证据冲突超过原问题单时停止扩大操作并归还决策权 |

当前 Codex 实现遵守以下默认值：

- 用户会话由 Sol / Frontier 主 Agent 托管。
- 每次创建子 Agent 必须显式选择 Terra 或 Luna，不得无意继承主模型。
- 全局子 Agent 兜底模型使用 Terra / Balanced。
- 默认不创建 Sol 子 Agent；子任务升级后由主 Sol 接管判断。
- 模型和推理预算按歧义、范围、风险、验证难度与可逆性选择，不以任务名称机械决定。

具体配置键、文件位置和端到端验证由后续 Codex 适配层负责，核心协议只保留能力层级语义。

## 5. 什么时候调用子 Agent

`NO_DELEGATION` 是正式、正常的路由结果，不表示编排失败。只有以下四道价值闸全部通过，
才选择 `DELEGATE`：

1. **独立**：存在两个以上互不依赖的调查、实现或验证任务，不共享高风险写入状态。
2. **有收益**：预计节省的时间或上下文显著高于说明、等待、Token、复核和整合成本。
3. **非阻塞**：主 Agent 等待期间仍有不重复且有价值的工作可推进。
4. **可验收**：子任务边界、输入、输出和验收可以单独说明，结果可用当前证据低成本复核。

主 Agent 约五分钟内可以完成并验证的任务，以及主线程下一步立即依赖其结果的任务，
默认 `NO_DELEGATION → DIRECT_MAIN`。小型线性任务、紧急阻塞任务、共享状态写入和
高风险外部操作也不为展示多 Agent 而拆分。

### 派遣容量与健康探针

派遣前必须预留后续验证、审查和一次恢复所需的 `reserved_slots`；计划中的 Worker 与
预留额度之和不得超过当前运行时实际可用的并发容量。容量由当前平台、账号和项目配置决定，
不得在核心协议中写死为某个数字。

第一个真实 Worker 是健康探针：主 Agent 必须确认它已实体化、可读取并处于可管理状态，
才允许继续 fan-out。健康探针失败时停止本批派遣，由主 Agent 直接完成或重新判断路线，
不得为碰运气反复创建空任务。

## 6. 委派问题单

每个子 Agent 只接收一个边界清楚的交付物。委派内容至少包含：

| 字段 | 要求 |
| --- | --- |
| 目标 | 一句话说明要解决什么 |
| 上下文与证据 | 提供完成任务所需的最小背景，不倾倒整段聊天 |
| 范围 | 明确可读、可写和禁止触碰的文件、系统或外部状态 |
| 输出与验收 | 指定要返回的结论、产物、测试证据和风险 |
| 执行配置 | 显式选择模型层级、推理预算、P0-P3 权限与验收方式 |
| 预算与升级 | 说明时间或工具预算，以及触发 `ESCALATE_TO_MAIN` 的条件 |
| 所有权与接口 | 分配互斥的文件、模块、章节或主题；同一文件只允许一个写入者，并说明与其他 Worker 的输入输出接口 |
| 执行纪律 | Worker 不得继续派遣 Agent；信息不足时报告缺口和证据，不猜测、不扩大范围 |

没有明确验收标准的任务不得为了并行而分发。

## 7. 回收、审查与验收

子 Agent 返回时必须说明：完成了什么、证据在哪里、修改了什么、验证结果和剩余风险。

主 Agent 随后负责：

1. 检查结果是否回答原问题单。
2. 用当前文件、测试或真实输出复核关键结论。
3. 处理不同 Worker 之间的冲突和重复。
4. 将结果整合回当前垂直切片，而不是扩大范围。
5. 统一向用户说明完成情况、证据、风险和下一步。

子 Agent 说“完成”不等于项目完成；最终完成声明只能由主 Agent 给出。

主 Agent 只有在产物已验证、结果已采纳且风险已记录后，才能关闭或归档对应 Worker。
平台不支持归档时，仍须记录同等的最终状态；未采纳、争议中或未验证的结果必须保留以便复核。

## 8. 失败、升级与降级

- Worker 发现范围扩大、证据冲突、连续工具失败，或触及认证、权限、敏感数据、数据库、
  公共 API、核心业务、生产环境和不可逆操作时，停止扩大操作并返回 `ESCALATE_TO_MAIN`。
- 升级包必须说明发现、已完成操作、未处理内容、当前证据和升级原因。
- 子 Agent 容量不足或不可用时，不自动换更强模型；先重新经过委派价值闸。
- 小型任务只等待一个合理窗口。若继续等待不如主 Agent 直接完成，状态转为
  `TIMEOUT → RECLAIMED`，主 Agent 按同一问题单顺序执行。
- 已由主 Agent 完成的任务不等待迟到结果阻塞交付。
- 高风险外部写入、部署、删除、凭据和最终 Git 发布不得无人复核地委派。
- 真实副作用仍需用户授权；多 Agent 不会扩大原任务权限。
- 尚未实体化的 Worker 与运行后超时的 Worker 必须分开处理，二者不得混淆：前者停止本批派遣并回到主 Agent，
  后者才进入 `TIMEOUT → RECLAIMED`。平台特有的故障名和处置见对应适配层。

最小状态机为：

```text
TRIAGE → DIRECT / DELEGATED → RUNNING → REVIEW → ACCEPTED
DELEGATED → SPAWNING → UNMATERIALIZED → STOP_BATCH → DIRECT
RUNNING → ESCALATED → REPLAN
RUNNING → TIMEOUT → RECLAIMED
RUNNING → FAILED → FALLBACK
REVIEW → REJECTED → REWORK
```

状态必须能回答：当前由谁负责、允许做到哪里、何时超时、失败后回到谁。当前协议先定义
状态和契约；持久任务图属于后续运行时能力，不要求一期立即引入特定编排框架。

## 9. 验收标准

编排引擎只有在以下条件成立时才算健康：

1. 用户只需要维护一条与主 Agent 的对话线。
2. 每个任务先得到 `NO_DELEGATION` 或 `DELEGATE` 的可解释判断。
3. 每次委派都有明确交付物、执行配置、权限、预算、升级条件和验收标准。
4. 基础任务不会无意消耗 Frontier 模型，推理强度不会被误当成权限。
5. 子 Agent 的结论经过主 Agent 复核后才进入最终交付。
6. 子 Agent 不可用、超时或越界时能升级、回收或退化为单 Agent 顺序执行。
