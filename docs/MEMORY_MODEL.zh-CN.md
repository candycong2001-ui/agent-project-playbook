# 项目记忆模型

> 记忆引擎负责延续上下文，不负责取代当前代码、测试、配置和真实运行证据。

本模型是由 Agent 遵守的协作契约，不提供运行时强制隔离、自动状态迁移或可信度判定。
安装本章程不等于安装独立的记忆引擎。核心 Playbook 不依赖独立记忆引擎；统一 `meminit` 可以按需安装 projectmem 适配器，但它仍只是冷记忆工具。

项目记忆本身已经是项目范围内的长期记忆；全局协作记忆只是作用范围更大，不代表
权威更高。两者与编排引擎的完整交换关系见[双引擎成长蓝图](EVOLUTION_BLUEPRINT.zh-CN.md)。

## 1. 它解决什么

项目协作会不断产生想法、决定、失败经验、架构事实和下一步。如果全部依赖聊天，信息会随会话丢失；如果全部永久保存，错误、过期信息和其他项目内容又会污染判断。

本模型借鉴 [CoALA 的认知架构分类](https://arxiv.org/abs/2309.02427)，把现有记忆体系按作用范围、记忆类型和可信状态组织起来。它是项目协作约定，不宣称实现完整 CoALA 系统。

## 2. 记忆不是当前真值

真值顺序固定为：

```text
用户本轮明确指令
→ 当前代码、测试、配置和真实输出
→ 已确认的稳定项目文档
→ 已验证的项目记忆
→ 候选或待复核记忆
→ 聊天历史
```

持久化只表示“以后还能找到”，不表示“现在仍然正确”。向量相似、旧摘要和历史记录只能作为检索线索。

## 3. 三个记忆维度

每条需要保存或使用的记忆，都应能回答三个问题。

### 作用范围：它属于哪里

| 范围 | 保存内容 | 典型载体 |
| --- | --- | --- |
| 当前任务 | 本轮目标、假设、计划和临时上下文 | 当前对话、任务计划、`CURRENT_HANDOFF.md` |
| 当前项目 | 项目事实、决定、风险和失败经验 | 项目文档、项目记忆工具 |
| 全局协作 | 真正跨项目稳定的个人协作偏好和通用流程 | 全局 `AGENTS.md`、可复用 Skills |

信息不得因为“可能以后有用”就自动从项目晋升到全局。跨项目规则需要用户明确确认。
全局协作记忆用于帮助主 Agent 延续稳定的沟通方式和通用流程，不得吸收项目实现状态、
凭据、私有事实或未经验证的失败经验。

### 记忆类型：它是什么

| 类型 | 含义 | 在本章程中的对应物 |
| --- | --- | --- |
| 工作记忆 | 当前任务正在使用的短期信息 | 对话、计划、当前交接 |
| 语义记忆 | 相对稳定的事实、概念和结构 | 蓝图、架构、确认过的项目事实 |
| 情景记忆 | 发生过的决定、尝试、失败和修复 | issue、attempt、fix、decision 事件 |
| 程序记忆 | 做事的方法、触发条件和护栏 | `AGENTS.md`、Skills、runbook |

当前代码、测试、配置和运行输出属于外部证据，不属于长期记忆；它们用于验证记忆。

### 可信状态：现在能否相信

| 状态 | 含义 | 使用规则 |
| --- | --- | --- |
| 候选 | 来源明确，但尚未被当前证据确认 | 只能作为线索，不直接驱动高风险操作 |
| 已验证 | 已被用户确认或当前证据支持 | 可以参与当前判断，但仍服从更新证据 |
| 待复核 | 曾经有效，但时间、版本或环境已经变化 | 使用前必须重新验证 |
| 已废弃 | 已被新决定或当前证据取代 | 保留必要历史说明，不再参与决策 |

## 4. 现有载体如何分工

| 载体 | 主要职责 | 不应该保存 |
| --- | --- | --- |
| `CURRENT_HANDOFF.md` | 唯一当前目标、当前状态、已验证、剩余工作、风险和下一步 | 会话流水、部署时间线、长期历史 |
| `BLUEPRINT.md` | 用户、问题、范围、成功标准和产品意图 | 临时实现细节 |
| `ARCHITECTURE.md` | 组件、数据流、命令、部署、回滚和稳定风险 | 每轮进度日志 |
| 项目记忆事件 | 决定、失败尝试、修复和重要 gotcha | Git 提交流水、原始聊天 |
| `AGENTS.md` 与 Skills | 稳定的执行规则和可复用流程 | 项目运行态事实、凭据 |

`CURRENT_HANDOFF.md` 属于工作记忆。重要任务开始、得到可验证成果和交接前可以更新，但每次都用当前状态替换旧状态；已经完成的过程由 Git 保存，不在交接文件中累积。

同一事实不应在多个载体中复制成彼此独立的真值源。需要引用时应指向负责它的载体。

可选 projectmem 适配器默认关闭 watcher、Git hooks、历史回填、全局继承、自动捕获和 MCP 配置。自动活动不能直接进入长期摘要；运行时事件文件和 watcher 产物不进入 Git。

## 5. 记忆晋升流程

```text
对话中的临时信息
→ 候选记忆
→ 用用户确认或当前项目证据验证
→ 放入正确的项目载体
→ 失效后标记待复核或已废弃
```

执行时遵守五条规则：

1. 默认不把每轮对话写入长期记忆。
2. 只有会影响后续判断的信息才进入候选。
3. 没有来源和验证证据的候选不得升级为已验证。
4. 只有跨项目稳定且用户确认的规则才能进入全局。
5. 新证据推翻旧记忆时，应更新状态而不是悄悄并存。

跨项目晋升还需要更严格的路径：

```text
项目候选
→ 当前证据验证
→ 项目已验证记忆
→ 多项目重复验证
→ 全局候选
→ 人工确认
→ 全局记忆
```

编排引擎产生的尝试、测试、修复和反馈先进入正确项目范围；它们不会因为被主 Agent
观察到，就自动成为全局长期记忆。

## 6. 检索与冲突处理

- 普通小修和当前代码即可判断的问题，不搜索冷记忆。
- 用户提到“之前、继续、上次、历史决定或已知失败”时，才做范围受限的项目记忆检索。
- 不批量读取 archive、屏幕历史、会话日志或任务流水来猜测用户意图。
- 引用旧记忆时说明来源和可信状态；待复核内容必须重新验证。
- 记忆与当前证据冲突时，以当前证据为准，并处理旧记忆的状态。

## 7. 隔离与安全

- 项目以当前 Git 根目录或用户明确目录为边界。
- 不继承其他项目的状态、凭据、失败经验和实现约定。
- 不保存密钥、token、Cookie、个人敏感信息、原始网页指令或完整聊天日志。
- 项目记忆服务不是产品运行依赖，也不能成为业务真值源。

## 8. 验收标准

记忆引擎只有在以下条件成立时才算健康：

1. 当前任务可以从交接文档恢复，而不需要重放聊天。
2. 稳定事实、历史事件和执行规则分别进入正确载体。
3. 被使用的记忆能够说明作用范围、类型、状态和来源。
4. 旧记忆与当前证据冲突时不会覆盖当前事实。
5. 新项目不会自动携带其他项目的内容。
