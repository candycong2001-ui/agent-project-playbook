# 人机项目协作章程

## 1. 章程解决什么

用户不必先掌握产品、架构、前端、后端、测试、Git 或多 Agent，才有资格开始项目。用户负责表达目标、感受、限制和确认关键方向；主 Agent 负责把混沌逐步转换成结构化、可验证、可交接的项目。

章程不是要求一开始就写齐全部文档，也不是固定瀑布流程。它由一条项目主线和两个后台引擎组成：项目主线保证工作持续向稳定交付收敛，记忆引擎保证上下文可延续，编排引擎保证专业能力被正确调用。

本文件保存完整方法，不要求每个项目把全文放进 `AGENTS.md`。项目根规则只负责稳定默认值和 Skill 路由；生命周期、委派和文档维护细则按需加载，避免普通任务长期携带无关上下文。

“探索、启动、实施”是人机协作模式；“问题发现、启动准备、MVP、功能扩展、稳定运行、维护优化”是项目生命周期阶段，两者不能混为一个字段。

## 2. 一条项目主线、两个后台引擎

```text
模糊想法
→ 探索
→ 启动
→ 实施
→ 最小垂直切片
→ 验证与交付
→ 新认识进入下一轮
```

两套引擎贯穿主线，但不取代主线：

- 记忆引擎回答“哪些信息值得保留、保存在哪里、现在是否可信”。
- 编排引擎回答“本轮由谁处理、使用什么能力层级、如何审查和验收”。

两台引擎形成一个受治理的成长闭环：

```text
理解 → 编排 → 执行 → 验证 → 记忆 → 更好的理解
```

记忆引擎向主 Agent 提供已验证的偏好、项目事实、历史决定和已知失败；编排引擎把
问题单、尝试、测试结果、修复证据和新风险送回正确的记忆范围。项目结果只有经过验证
才能进入项目长期记忆；跨项目规则还必须经过重复验证和用户确认，才能晋升全局。

用户不需要分别管理两套引擎。主 Agent 是唯一协作入口，负责在每轮工作中调用它们。
完整的闭环、长期护栏和演进路线见[双引擎成长蓝图](EVOLUTION_BLUEPRINT.zh-CN.md)。

## 3. 三种协作模式

### 探索模式

- 接受不完整想法、生活化表达和不确定目标。
- 通过讨论、调研、比较和只读验证理解真实问题。
- 默认不修改项目，不要求用户提前准备完整需求。

### 启动模式

- 当用户明确准备落地时，收敛目标用户、核心问题、边界和成功标准。
- 建立最小项目骨架、命令入口、工作目录、测试入口和交付边界。
- 选出第一条最小可验证闭环，但不默认直接编码。

### 实施模式

- 先判断项目阶段和本轮最需要的交付物。
- 再形成问题单、垂直切片和角色分发。
- 按风险完成实现、验证、文档同步和统一交付。

模式可以来回切换。测试产生的新认识可以回到探索；方向改变时可以回到启动。

## 4. Design Thinking 映射

| Design Thinking | 主要模式 | 在协作中的作用 |
| --- | --- | --- |
| Empathize 共情 | 探索 | 理解用户、场景、感受和真实阻力，不急于给方案 |
| Define 定义 | 探索 | 把观察收敛成问题陈述、目标用户、成功标准和边界 |
| Ideate 构思 | 探索 → 启动 | 比较方向、暴露假设、选择准备验证的路线 |
| Prototype 原型 | 启动 → 实施 | 将路线压缩成本轮最小可验证交付物和第一条垂直切片 |
| Test 测试 | 实施 | 用验收证据验证交付物，并把新认识送回前一模式 |

## 5. 自动两级任务路由

主 Agent 按下面的顺序工作：

```text
项目阶段判断
→ 本轮交付物
→ 问题单
→ 最小垂直切片
→ 能力与角色分发
→ 整合、验证、交付
```

### 第一级：项目阶段与本轮交付物

先判断项目是在理解问题、准备启动、构建 MVP、扩展功能、稳定运行，还是维护优化。再选择本轮最需要的交付物，例如：

- 问题定义、MVP 范围或用户故事。
- 产品蓝图、架构或数据模型。
- 原型、演示或代码切片。
- 测试证据、文档、部署或回滚方案。

新项目不得因为用户提到“做一个产品”就默认直接编码。

协作模式描述“这一轮我们怎样合作”，项目阶段描述“产品当前走到哪里”。例如，一个已经稳定运行的项目也可以因为新方向重新进入探索模式。

### 第二级：问题单与切片分类

确定交付物后，问题单应包含：

- 用户感受或当前证据。
- 推断的问题与本轮交付物。
- 验收标准和风险。
- 最小垂直切片与暂不处理项。

Bug、功能、UI、体验、重构、性能、数据、测试、文档和部署是切片级分类，不替代项目阶段判断。用户无需自己分类。

## 6. 垂直切片纪律

- 每轮只完成一个可以独立验收的闭环。
- 需要时覆盖 UI、后端和数据；相关测试与文档属于完成条件。
- 不把无关重构、视觉美化、性能优化、部署和历史兼容塞进同一轮。
- 重构先保护现有行为；性能优化先测量；UI/体验必须有可观察的验收标准。

## 7. 主 Agent 托管模式

默认采用 Manager Pattern / Orchestrator–Worker，而不是让用户直接驾驭多个 Agent：

- 用户只与主 Agent 沟通目标、感受、限制和确认事项。
- 主 Agent 负责理解语义、判断阶段、选择交付物、拆分任务和确定能力层级。
- 子 Agent 只接收边界清楚的执行任务，并返回证据、产物和风险。
- 主 Agent 必须检查子 Agent 的结果，处理冲突，完成最终验证并统一交付。
- 每个任务先经过委派价值闸；`NO_DELEGATION` 是正常路由结果，简单线性任务由主 Agent 直接完成。
- 只有独立、有明显收益、非阻塞且可低成本验收时才委派；模型、推理预算和权限分别判断。
- 子 Agent 发现范围或风险超过原问题单时停止扩大操作，以 `ESCALATE_TO_MAIN` 归还决策权。
- 派遣前预留验证、审查和恢复容量；首个真实 Worker 必须通过可读取的健康探针后，才继续并行派遣。
- 任务包必须分配互斥所有权和 Worker 接口；Worker 不得继续派遣，信息不足时报告缺口而不猜测。
- 只有主 Agent 验证并采纳产物后，才能关闭或归档对应 Worker；未实体化与运行后超时的失败状态不得混淆。

这不是 Handoff 模式：对话控制权和最终责任始终留在主 Agent。完整规则见[主 Agent 托管与编排模型](ORCHESTRATION_MODEL.zh-CN.md)。

## 8. 风险、验证与外部副作用

- 只读检查可以自动进行。
- 没有相反证据时，默认按本地、单用户、低风险项目处理，不要求生产流程。
- 低风险改动运行直接相关的最小验证。
- 中风险改动增加影响范围测试和回归检查。
- 主 Agent 根据运行服务、共享状态、真实用户、凭据和外部写入自动提升风险，不要求用户先说出“生产”或“高风险”。
- 高风险操作先核对状态，再选择必要的 dry-run、备份和回滚路径。
- 部署、删除、真实外部写入、凭据操作和最终 Git 发布需要明确授权和主 Agent 复核。
- 没有验证证据不得宣称完成。

### 正式项目的发布隔离

- Playbook 默认安装 `simple` 配置；只有当前证据确认存在生产运行面时才选择 `production` 配置，后者增加按影响面工作的发布 Skill 和本地 worktree 辅助工具。
- 当前证据确认存在生产运行面时，优先遵守项目自己的运维文档和生产 Skill，不把一套固定命令复制到所有项目。
- 先按影响面分类：文档通常不触碰生产；前端、后端、常驻任务和依赖只更新受影响部分；状态结构、数据迁移和真实外部写入单独升级。
- 任务分支、独立 worktree、环境隔离和固定运行版本只在当前项目的生产规则要求时启用，不作为普通本地项目的默认负担。
- `main` 只表示已审核源码，不表示已经部署；真正改变运行版本、进程、数据或外部状态时必须执行项目定义的发布动作。
- 数据迁移和真实外部写入是独立高风险切片，需要当前状态核对、适用的备份或回滚准备以及明确授权。

`production-release-gate` 只提供分流原则；当前项目的真实构建、进程、备份、健康检查和回滚命令必须来自项目自身文档和验证结果。

## 9. 项目结构与记忆

- 当前用户指令、代码、测试和真实输出高于历史记忆。
- 项目记忆本身是项目范围内的长期记忆；全局记忆作用范围更大，但权威不高于当前项目证据。
- 任务记忆只服务本轮；项目记忆延续项目；全局记忆只保存用户确认的稳定协作偏好和通用流程。
- `AGENTS.md` 保存当前项目的程序性执行规则。
- `BLUEPRINT.md` 和 `ARCHITECTURE.md` 保存稳定的语义记忆。
- `CURRENT_HANDOFF.md` 保存唯一当前目标、当前状态、验证、剩余工作、风险和下一步；更新时替换旧内容，不追加会话或部署流水。
- 事件记忆只保存经过判断的决定、失败经验和风险，不保存提交活动、密钥或原始聊天。
- 项目按 Git 根目录或明确目录隔离，不自动继承其他项目的事实、状态、凭据和失败经验。
- 可选 projectmem 只作为当前项目冷记忆；watcher、Git 自动采集、历史回填、全局继承和 MCP 默认关闭。

重要任务开始、得到可验证成果和交接前是 `CURRENT_HANDOFF.md` 的三个更新节点。Git 保存历史，交接文件只保留接手者现在继续工作所需的内容。

记忆必须同时标明作用范围、类型和可信状态；完整规则见[项目记忆模型](MEMORY_MODEL.zh-CN.md)。
项目经验晋升到全局时，必须遵守“项目候选 → 证据验证 → 多项目重复验证 → 全局候选
→ 人工确认”的路径，不得因为一次成功或失败自动形成永久规则。

## 10. 一轮工作的完成条件

一轮工作只有同时满足以下条件才算完成：

1. 本轮交付物达到验收标准。
2. 相关测试或验证有明确证据。
3. 本轮实际受影响的蓝图、架构或当前交接已同步；普通小修不制造无关文档改动。
4. 剩余风险和暂不处理项被明确记录。
5. 用户得到一个统一结果和一个具体下一步。
